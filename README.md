# 🌌 Kirkland Sky Calendar

[![Update Astronomy Calendar](https://github.com/kplus10/kirkland-sky-calendar/actions/workflows/update-calendar.yml/badge.svg)](https://github.com/kplus10/kirkland-sky-calendar/actions/workflows/update-calendar.yml)

A location-aware astronomy calendar for **Kirkland, Washington**, generated with Python and [Skyfield](https://rhodesmill.org/skyfield/).

The project calculates interesting sky events, filters or scores them for practical visibility from Kirkland, and publishes the results as a standards-friendly `.ics` feed that can be subscribed to from Google Calendar, Apple Calendar, Outlook, and other calendar applications.

The goal is simple:

> **Show the sky events that are actually worth knowing about from Kirkland, without filling the calendar with minor astronomical events.**

---

## 📅 Subscribe to the calendar

The generated calendar is written to:

```text
docs/sky-events.ics
```

When GitHub Pages is configured to publish the `docs/` folder from the `main` branch, the subscription URL is:

```text
https://kplus10.github.io/kirkland-sky-calendar/sky-events.ics
```

### Google Calendar

On the desktop version of Google Calendar:

1. Open Google Calendar.
2. Under **Other calendars**, click **+**.
3. Select **From URL**.
4. Paste:

```text
https://kplus10.github.io/kirkland-sky-calendar/sky-events.ics
```

5. Click **Add calendar**.

This is a subscription, not a one-time import. The feed is regenerated by GitHub Actions and Google Calendar periodically refreshes subscribed calendars.

> Google controls its own refresh interval, so a successful GitHub Actions update may take some time to appear in Google Calendar.

# ✨ What the calendar currently includes

The primary generator is:

```text
generate_skyfield_calendar.py
```

It creates a rolling calendar covering approximately:

- the previous **31 days**
- the next **730 days** (~24 months)

This avoids hard-coded years and keeps the feed useful as the project continues running.

## 🌕 Named full moons

Full-moon times are calculated with Skyfield using the JPL ephemeris.

Traditional monthly names are assigned using the local Kirkland calendar date:

| Month | Moon name |
|---|---|
| January | Wolf Moon |
| February | Snow Moon |
| March | Worm Moon |
| April | Pink Moon |
| May | Flower Moon |
| June | Strawberry Moon |
| July | Buck Moon |
| August | Sturgeon Moon |
| September | Corn Moon |
| October | Hunter's Moon |
| November | Beaver Moon |
| December | Cold Moon |

Each calendar event includes:

- exact full-moon time
- Earth–Moon distance
- Moon altitude from Kirkland at exact full phase

---

## 🌾 Harvest Moon

The Harvest Moon is calculated as the **full moon nearest the actual Northern Hemisphere Autumnal Equinox**.

The equinox itself is calculated with Skyfield rather than approximated as a fixed September date.

Depending on the year, an event may appear as something like:

```text
Harvest Moon 🌾🌕 (Corn Moon)
```

or:

```text
Super Harvest Moon 🌾🌕
```

---

## 🔵 Blue Moons

Two Blue Moon definitions are supported.

### Monthly Blue Moon

The second full moon in the same local calendar month.

Example:

```text
Blue Moon 🔵🌕
```

### Seasonal Blue Moon

The third full moon in an astronomical season that contains four full moons.

Example:

```text
Seasonal Blue Moon 🔵🌕
```

## 🌕 Supermoons

The project uses a practical, configurable supermoon rule.

A full moon is currently marked as a supermoon when:

```text
Earth–Moon distance at full phase ≤ 360,000 km
```

and the full moon occurs within:

```text
24 hours of the nearest lunar perigee
```

The generator searches for the nearby perigee and includes both the full-moon distance and perigee information in the event description.

> There is no single official astronomical definition of "supermoon," so different published calendars may use slightly different criteria.

# 🌑 Lunar eclipses and Blood Moons

Skyfield's lunar-eclipse calculations are used to identify eclipses during the rolling calendar window.

The calendar intentionally includes the visually meaningful eclipse types:

- **Partial lunar eclipses**
- **Total lunar eclipses / Blood Moons**

Penumbral-only eclipses are omitted to keep the calendar focused.

For each eclipse, the generator checks local Kirkland geometry and requires the Moon to be above the horizon during at least part of the eclipse while the Sun is below the horizon.

Total lunar eclipses are labeled:

```text
Blood Moon 🩸🌕 — Total Lunar Eclipse
```

Descriptions include:

- global maximum time
- Moon altitude at maximum
- whether the global maximum itself is visible from Kirkland
- umbral magnitude

If the eclipse is only partly visible locally, the event explains that the global maximum is below the Kirkland horizon.

---

# ☀️ Solar eclipses visible from Kirkland

The generator checks each calculated new moon for local apparent Sun/Moon disk overlap.

It uses topocentric geometry from Kirkland and can classify locally visible events as:

- Partial solar eclipse
- Annular solar eclipse
- Total solar eclipse

The current implementation records the best local overlap time and includes:

- Sun altitude
- apparent Sun–Moon center separation
- locally computed eclipse classification

> Detailed first/second/third/fourth contact times are not yet calculated.

---

# 🪐 Bright-planet conjunctions

The calendar searches pairwise combinations of:

- Mercury
- Venus
- Mars
- Jupiter
- Saturn

A conjunction is considered interesting when the closest apparent separation is within the configured threshold:

```text
3°
```

Close events under 1° are highlighted as:

```text
Very Close Venus–Jupiter Conjunction 🪐
```

The search first locates candidate minima and then numerically refines the closest-approach time instead of relying only on coarse daily sampling.

## Kirkland visibility filtering

A conjunction is only added when a practical viewing opportunity is found.

The recommended viewing time requires:

```text
planet altitude ≥ 10°
Sun altitude ≤ -6°
```

In other words, both objects need to be comfortably above the horizon and the sky must be at least civil twilight or darker.

Descriptions include:

- exact closest-approach time
- minimum angular separation
- recommended Kirkland viewing time
- angular separation at the recommended time
- altitude of each planet
- Sun altitude

---

# 🪐 Multi-planet groupings

The calendar looks for opportunities when **three or more bright planets** are visible together.

The current grouping rule requires:

```text
3+ planets above 10°
```

during twilight/darkness and within roughly:

```text
90° along the ecliptic
```

Consecutive qualifying nights are collapsed into a single highlight event so the calendar does not get flooded with nearly identical entries.

Events can appear as:

```text
3-Planet Grouping 🪐
```

or:

```text
Major 4-Planet Grouping 🪐
```

The description lists the planets, approximate altitudes, grouping span, and recommended viewing time.

> "Planet parade" is an informal term. The project's grouping rule is intentionally practical rather than an official astronomical classification.

---

# 🔭 Planetary oppositions

The generator calculates oppositions for:

- Mars
- Jupiter
- Saturn

Opposition generally places an outer planet near its best observing period because it is opposite the Sun in the sky, visible for much of the night, and often near its brightest apparent state.

Events look like:

```text
Jupiter at Opposition 🔭
```

Each event includes:

- exact opposition time
- recommended Kirkland viewing time
- approximate altitude
- Sun altitude at the recommended time

---

# ✨ Venus greatest elongations

The calendar identifies Venus's greatest eastern and western elongations.

These correspond to particularly favorable viewing periods:

- **Greatest Eastern Elongation** → evening visibility
- **Greatest Western Elongation** → morning visibility

Example:

```text
Venus Greatest Eastern Elongation ✨
```

The event description includes the calculated elongation from the Sun and a recommended local viewing time.

---

# 🌠 Major meteor showers

Meteor showers are generated from a curated list of major annual showers.

Currently included:

| Shower | Typical ideal ZHR* |
|---|---:|
| Quadrantids | ~80 |
| Lyrids | ~18 |
| Eta Aquariids | ~50 |
| Southern Delta Aquariids | ~25 |
| Perseids | ~100 |
| Orionids | ~20 |
| Leonids | ~15 |
| Geminids | ~120 |
| Ursids | ~10 |

\*ZHR is the approximate zenithal hourly rate under ideal dark-sky conditions. Actual observed rates from Kirkland will often be lower.

Rather than hard-coding a calendar date, the generator solves for each shower's configured **solar longitude** for the relevant year.

It then evaluates the viewing window around the peak using:

- Sun altitude
- radiant altitude
- Moon altitude
- Moon illumination
- distance in time from the calculated peak

The resulting event includes a recommended viewing time and a simple Moon-condition rating such as:

```text
excellent
good
challenging
```

> Weather, local light pollution, trees, buildings, and sky transparency are not currently included.

# 📍 Location and visibility model

The calendar is tuned for Kirkland, Washington using approximate city-center coordinates:

```python
KIRKLAND_LAT = 47.6769
KIRKLAND_LON = -122.2060
```

Timezone:

```text
America/Los_Angeles
```

These city-level coordinates are more than precise enough for the event types in this project.

Astronomical calculations are performed with UTC internally, while event descriptions show Pacific local time when useful. The ICS feed itself stores event timestamps in UTC so calendar applications can correctly display them in the subscriber's timezone.

## Default visibility thresholds

```python
MIN_PLANET_ALT_DEG = 10.0
MAX_SUN_ALT_FOR_PLANETS_DEG = -6.0
CONJUNCTION_THRESHOLD_DEG = 3.0
PLANET_GROUPING_MAX_SPAN_DEG = 90.0
```

These are project choices intended to produce a useful calendar rather than every technically possible event.

# 🗓 Rolling calendar window

The generator dynamically calculates its range from the time it runs:

```python
LOOKBACK_DAYS = 31
LOOKAHEAD_DAYS = 730
```

So the feed normally includes:

```text
~1 month in the past
through
~24 months in the future
```

The additional lookback helps calendar clients preserve recently completed events while the rolling future window keeps the feed automatically current.

The calculation window is extended beyond the output range internally so boundary-dependent astronomy events can still be detected correctly.

---

# 🆔 Stable calendar event IDs

Each event receives a deterministic iCalendar UID derived from a logical event key using SHA-1.

This is important for subscribed calendars.

Instead of generating a new random UUID every month, the same logical astronomy event keeps the same UID when the calendar is regenerated.

That helps Google Calendar and other clients recognize an updated event as the same event rather than creating duplicates.

# 📄 ICS output

The generated file includes standard calendar metadata:

```text
X-WR-CALNAME:Kirkland Sky Highlights
X-WR-TIMEZONE:America/Los_Angeles
```

Events also include:

- stable `UID`
- `DTSTAMP`
- `DTSTART`
- `DTEND`
- `SUMMARY`
- `DESCRIPTION`
- `LOCATION`
- `CATEGORIES`
- `PRIORITY`
- transparent/free-time status

Long iCalendar lines are folded at the RFC-friendly 75-byte boundary.

Event categories currently include:

```text
Moon
Eclipse
Planets
Meteor Shower
```

Priority values are used to distinguish major "don't miss" events from routine astronomy entries.

# ⚠️ Current limitations

The calendar is astronomy-aware and location-aware, but it is not yet weather-aware.

## No weather/cloud filtering

An event can be astronomically ideal and still be hidden by Pacific Northwest clouds.

The generator does not currently use:

- live weather forecasts
- cloud-cover forecasts
- smoke/haze forecasts
- local sky transparency

## Solar eclipse contacts are not yet included

Solar eclipses are locally detected and classified, but detailed contact times are not currently generated.

## Meteor shower rates are approximate

The listed ZHR is an ideal reference value, not a forecast for Kirkland.

Real observed rates depend on:

- light pollution
- cloud cover
- radiant altitude
- Moon brightness
- shower variability
- observer experience

## Meteor-shower peak definitions are data-driven

Skyfield does not provide a meteor-shower catalog. The repository contains a curated table of shower solar longitudes, radiants, and approximate ZHR values. Skyfield is then used to solve for the corresponding solar longitude each year and evaluate local viewing conditions.

## Supermoon is a project definition

"Supermoon" is not a formal IAU astronomical category. The thresholds in this project are explicitly configurable.

## Planet grouping is a project definition

Terms such as "planet parade" are informal. This project uses a practical visibility-and-ecliptic-span rule to decide when a grouping is worth adding.

## No automatic comet discovery yet

Notable comet events are not currently generated.

A robust implementation would need a regularly updated comet orbital/catalog data source rather than relying only on the static planetary ephemeris.

# 🎯 Design philosophy

The project intentionally prefers **useful observing opportunities** over an exhaustive astronomical catalog.

A technically interesting event is not necessarily useful if:

- it occurs below the Kirkland horizon
- the planets are only a few degrees above the horizon
- the event occurs in daylight
- a meteor shower is overwhelmed by the Moon
- multiple nights would produce nearly identical calendar entries

Where possible, the generator therefore calculates a **recommended local viewing time** rather than simply placing the event at its global astronomical instant.

The intended question is:

> **"What interesting sky event can I actually go outside and see from Kirkland?"**

---

# 🔬 Accuracy and interpretation

Positions and astronomical event times are calculated with Skyfield and the JPL DE440s ephemeris.

The astronomy geometry should be accurate enough for casual observing and planning, but the project's classification rules and recommendation thresholds are deliberately opinionated.

"Visible from Kirkland" means the event passes the project's astronomical visibility tests. It does **not** guarantee a clear view from a specific house, street, or observing site.

Actual visibility can still be affected by:

- cloud cover
- rain
- wildfire smoke
- haze
- local terrain
- buildings
- trees
- light pollution

For solar observing, always use proper certified solar-viewing equipment. Never look directly at the Sun without appropriate eye protection.

# 🛠 Troubleshooting

## `can't open file generate_skyfield_calendar.py`

Confirm the filename is exactly:

```text
generate_skyfield_calendar.py
```

and that `.github/workflows/update-calendar.yml` uses the same spelling.

## `de440s.bsp` errors

Confirm:

```text
de440s.bsp
```

exists in the repository root.

The generator loads it with:

```python
eph = load("de440s.bsp")
```

## Workflow succeeds but Google Calendar has not updated

First open the published `.ics` URL directly and confirm that the generated feed contains the new data.

Google controls how often subscribed calendars are refreshed, so Google Calendar may lag behind the GitHub Pages file.

## Workflow cannot push the generated file

Verify the workflow contains:

```yaml
permissions:
  contents: write
```

Also check the repository's Actions settings if GitHub refuses automated pushes.

## No calendar change was committed

This can be normal. If the generated `docs/sky-events.ics` is identical to the committed version, the workflow has nothing new to commit.
